# Multi-process Firedancer cluster (Alpenglow)

`test_firedancer_cluster` runs several full Firedancer validators on one
Linux host and asserts that every one of them roots blocks. Each
validator is a separate process and all of that validator's tiles run as
threads in it. This is a development and fuzzing tool, not a production
deployment mode.

The test reads its node configurations from the environment:

| Variable | Meaning | Default |
|---|---|---|
| `FD_CLUSTER_CONFIGS` | Colon-separated node config paths, in order | none, test skips |
| `FD_CLUSTER_ROOT_SLOT` | Slot every validator must root | `8` |
| `FD_CLUSTER_TIMEOUT_S` | Seconds allowed to reach it | `180` |

With `FD_CLUSTER_CONFIGS` unset the test logs a skip and passes, so it is
safe to leave in the normal test run.

The paths below use `/cluster` as an example. The node configs are not
generated by the test or checked into the repository: they contain
host-specific paths, ports, identities, and CPU assignments.

## 1. Build

```sh
make -j firedancer-dev test_firedancer_cluster
```

## 2. Create the identities and the shared Alpenglow genesis

A cluster needs one genesis naming every validator, with a BLS key per
validator and Alpenglow active at slot 0. This repository's genesis
stage only builds a single-validator genesis, so the file comes from
Agave's `solana-genesis`. The vendored `agave/` tree is Alpenglow
capable, but it is meant to be linked into a Firedancer binary, so
building a standalone binary from it needs Firedancer's version symbols
plus a stub for one extern the validator normally provides:

```sh
make -j lib/libfdctl_version.a lib/libfd_util.a

cat > /tmp/fd_ext_stub.c <<'STUB'
int fd_ext_larger_shred_limits_per_block( void ) { return 0; }
STUB
cc -O2 -fPIC -c -o /tmp/fd_ext_stub.o /tmp/fd_ext_stub.c
ar rcs /tmp/libfd_ext_stub.a /tmp/fd_ext_stub.o

cd agave && env --unset=LDFLAGS \
  RUSTFLAGS="-L $(realpath ../build/native/gcc/*/lib) -L /tmp \
             -lfdctl_version -lfd_util -lfd_ext_stub" \
  ./cargo build --release -p solana-genesis --bin solana-genesis
```

Scope the build with `-p solana-genesis`. Building the whole workspace,
or `solana-keygen`, pulls in a hardware-wallet dependency that needs
`libudev-dev`.

Any `solana-keygen` with a `bls_pubkey` subcommand works for the keys.
It signs the fixed message `bls-key-derive-alpenglow` with the identity
key and uses that signature as BLS key material, which is exactly what
Firedancer's sign tile does, so the derived keys agree. Check both
tools before continuing:

```sh
agave/target/release/solana-genesis --help | grep -- --alpenglow
solana-keygen bls_pubkey --help
```

Create a writable cluster directory plus identity, vote, stake, and
faucet keypairs:

```sh
sudo install -d -o "$(id -un)" -g "$(id -gn)" /cluster
mkdir -p /cluster/keys /cluster/ledger /cluster/logs \
  /cluster/node-0 /cluster/node-1 /cluster/node-2

solana-keygen new --no-bip39-passphrase --silent --force \
  --outfile /cluster/keys/faucet.json

for i in 0 1 2; do
  solana-keygen new --no-bip39-passphrase --silent --force \
    --outfile "/cluster/keys/identity-$i.json"
  solana-keygen new --no-bip39-passphrase --silent --force \
    --outfile "/cluster/keys/vote-$i.json"
  solana-keygen new --no-bip39-passphrase --silent --force \
    --outfile "/cluster/keys/stake-$i.json"
done

BLS_0=$(solana-keygen bls_pubkey /cluster/keys/identity-0.json)
BLS_1=$(solana-keygen bls_pubkey /cluster/keys/identity-1.json)
BLS_2=$(solana-keygen bls_pubkey /cluster/keys/identity-2.json)
```

There is no separate BLS secret file. Firedancer deterministically
derives the matching BLS secret from each identity keypair when it
starts.

Create one genesis containing all three validators:

```sh
solana-genesis \
  --alpenglow \
  --cluster-type development \
  --ledger /cluster/ledger \
  --slots-per-epoch 256 \
  --faucet-pubkey /cluster/keys/faucet.json \
  --faucet-lamports 500000000000000000 \
  --bootstrap-validator \
    /cluster/keys/identity-0.json \
    /cluster/keys/vote-0.json \
    /cluster/keys/stake-0.json \
  --bootstrap-validator-bls-pubkey "$BLS_0" \
  --bootstrap-validator \
    /cluster/keys/identity-1.json \
    /cluster/keys/vote-1.json \
    /cluster/keys/stake-1.json \
  --bootstrap-validator-bls-pubkey "$BLS_1" \
  --bootstrap-validator \
    /cluster/keys/identity-2.json \
    /cluster/keys/vote-2.json \
    /cluster/keys/stake-2.json \
  --bootstrap-validator-bls-pubkey "$BLS_2"
```

`--alpenglow` is required: it activates Alpenglow at genesis and embeds
the development genesis certificate. Record the command's
`Genesis hash:` value. Every validator must use that exact hash and the
resulting `/cluster/ledger/genesis.bin`.

Each `--bootstrap-validator-bls-pubkey` corresponds to the immediately
preceding `--bootstrap-validator`; keep the two repeated argument lists
in the same order.

## 3. Create `node-0.toml`, `node-1.toml`, and `node-2.toml`

Every node loads the same trusted local `genesis.bin` while followers
still use node 0 as a gossip entrypoint. `development.bootstrap = true`
selects that startup mode: the genesis and IP-echo tiles then ignore
gossip entrypoints, while the gossip tiles keep them for peer discovery.
This deliberately bypasses follower snapshot restore.

Start with this node 0 override. Replace `<non-root-user>`,
`<GENESIS_HASH>`, and `<NODE_0_CPU_LIST>`:

```toml
name = "fd-cluster-0"
user = "<non-root-user>"
telemetry = false

[paths]
    base = "/cluster/node-0"
    identity_key = "/cluster/keys/identity-0.json"
    vote_account = "/cluster/keys/vote-0.json"
    genesis = "/cluster/ledger/genesis.bin"

[log]
    path = "/cluster/node-0/firedancer.log"

[gossip]
    entrypoints = []
    host = "127.0.0.1"
    port = 8001

[snapshots]
    genesis_download = false

[consensus]
    expected_genesis_hash = "<GENESIS_HASH>"
    wait_for_vote_to_start_leader = false

[accounts]
    max_accounts = 65536
    cache_size_gib = 3

[runtime]
    max_live_slots = 64
    max_fork_width = 4
    program_cache_size_mib = 256

[layout]
    affinity = "<NODE_0_CPU_LIST>"
    net_tile_count = 1
    quic_tile_count = 1
    resolv_tile_count = 1
    verify_tile_count = 1
    gossvf_tile_count = 1
    execle_tile_count = 1
    execrp_tile_count = 1
    snapdc_tile_count = 1
    snapzp_tile_count = 1
    snapsv_tile_count = 1
    snapsv_io_worker_count = 1
    shred_tile_count = 1
    sign_tile_count = 2
    enable_block_production = true
    enable_snapshot_production = false

[hugetlbfs]
    mount_path = "/mnt/.fd-cluster-0"
    max_page_size = "huge"

[net]
    provider = "socket"
    interface = "lo"
    bind_address = "127.0.0.1"
    ingress_buffer_size = 1024

[tiles.gossip]
    max_entries = 8192

[tiles.quic]
    max_concurrent_connections = 512
    max_concurrent_handshakes = 64
    txn_reassembly_count = 1024
    regular_transaction_listen_port = 9001
    quic_transaction_listen_port = 9007

[tiles.verify]
    signature_cache_size = 65534
    receive_buffer_size = 1024

[tiles.dedup]
    signature_cache_size = 65534

[tiles.pack]
    max_pending_transactions = 4096

[tiles.replay]
    max_transaction_lookahead_buffer_size = 4096

[tiles.shred]
    max_pending_shred_sets = 1024
    shred_listen_port = 8003
    shred_cache_size_mib = 64
    additional_shred_destinations_leader = [
        "127.0.0.1:8103",
        "127.0.0.1:8203",
    ]

[tiles.repair]
    repair_client_listen_port = 8701
    slot_max = 128

[tiles.rotor]
    slot_max = 128

[tiles.rserve]
    repair_serve_listen_port = 8702
    shred_storage_limit_gib = 1

[tiles.txsend]
    txsend_src_port = 9006

[tiles.metric]
    prometheus_listen_port = 7999

[tiles.gui]
    enabled = false

[tiles.rpc]
    enabled = false

[development]
    alpenglow = true
    bootstrap = true

[development.runtime]
    max_stake_accounts = 4096
    max_stake_accounts_fallback = 65536
    max_vote_accounts = 64

[development.votor]
    quic_client_listen_port = 8005
    quic_server_listen_port = 8004

[development.gossip]
    allow_private_address = true

[development.genesis]
    validate_genesis_hash = false

[development.accdb]
    partition_size_gib = 1
```

Copy it to `node-1.toml` and `node-2.toml`, then apply this matrix. All
other values, especially `paths.genesis` and
`consensus.expected_genesis_hash`, stay the same.

| Setting | node 0 | node 1 | node 2 |
|---|---:|---:|---:|
| `name` | `fd-cluster-0` | `fd-cluster-1` | `fd-cluster-2` |
| `paths.base` | `/cluster/node-0` | `/cluster/node-1` | `/cluster/node-2` |
| identity/vote suffix | `0` | `1` | `2` |
| `log.path` | `/cluster/node-0/firedancer.log` | `/cluster/node-1/firedancer.log` | `/cluster/node-2/firedancer.log` |
| `hugetlbfs.mount_path` | `/mnt/.fd-cluster-0` | `/mnt/.fd-cluster-1` | `/mnt/.fd-cluster-2` |
| `gossip.entrypoints` | `[]` | `["127.0.0.1:8001"]` | `["127.0.0.1:8001"]` |
| gossip port | `8001` | `8101` | `8201` |
| shred port | `8003` | `8103` | `8203` |
| Votor server/client | `8004` / `8005` | `8104` / `8105` | `8204` / `8205` |
| repair client/server | `8701` / `8702` | `8801` / `8802` | `8901` / `8903` |
| TPU UDP/QUIC | `9001` / `9007` | `9101` / `9107` | `9201` / `9207` |
| txsend source | `9006` | `9106` | `9206` |
| metrics | `7999` | `8099` | `8199` |
| leader shred destinations | `8103, 8203` | `8003, 8203` | `8003, 8103` |

The TPU QUIC port must always equal the regular TPU port plus six. Any
other enabled listener, including an RPC or snapshot HTTP server, also
needs a unique port. The explicit leader shred destinations make
delivery deterministic in this small loopback cluster.

Two validators must not share both `name` and `hugetlbfs.mount_path`: a
workspace file is named `<name>_<workspace>`, so they would corrupt each
other. The test refuses to start such a pair.

The small accounts, slot, fork, and cache values above are a smoke-test
profile. Measure the exact total for the current configs with `mem`; the
three-node profile above needs about 11.3 GiB of 2 MiB huge pages per
node. Raise `runtime.max_live_slots` and the associated pools for longer
fuzz campaigns. A 64-slot pool can fill if a whole validator is
suspended while the rest of the cluster keeps advancing.

### Memory

The profile above sets both the cluster's account bounds and its traffic
buffers explicitly. Reducing only stake-account bounds and QUIC
connections still leaves several GiB reserved for mainnet-scale queues.
On the 64-slot Alpenglow topology, the additional changes reduce the
`mem --sort --json` total from 19.53 GiB to 11.24 GiB per node (42.5%),
or about 33.7 GiB for three nodes. These totals include workspace page
rounding and tile stacks; they describe reservation, not observed RSS.

| Setting | Previous profile | Cluster value | Approximate saving |
|---|---:|---:|---:|
| `tiles.shred.max_pending_shred_sets` | 32768 | 1024 | 2.62 GiB across store and shred |
| `tiles.pack.max_pending_transactions` | 65524 | 4096 | 854 MiB |
| `tiles.dedup.signature_cache_size` | 33554430 | 65534 | 767 MiB |
| `tiles.gossip.max_entries` | 524288 | 8192 | 747 MiB |
| `tiles.replay.max_transaction_lookahead_buffer_size` | 65536 | 4096 | 735 MiB |
| `net.ingress_buffer_size` | 16384 | 1024 | 735 MiB across gossip and network links |
| `tiles.quic.txn_reassembly_count` / `tiles.verify.receive_buffer_size` | 131072 / 16384 | 1024 / 1024 | 586 MiB |
| `runtime.program_cache_size_mib` | 512 | 256 | 256 MiB |
| `tiles.verify.signature_cache_size` | 4194302 | 65534 | 95 MiB |

Removing rotor's unused loose-memory reservation saves another 1 GiB;
all of its owned allocations are already included in its scratch layout.
Use the newly built binary under `build/native/gcc/*/bin/` when measuring;
an older copy at `build/firedancer-dev` will still reserve that memory.

Smaller queues suit a low-traffic local cluster. Under load they can
increase packet loss, cache misses, transaction eviction, or repair
traffic. Raise them for throughput tests or delayed-network scenarios.
The 256 MiB program cache is close to the current 252 MiB minimum for
64 live slots; increase it when testing larger or more numerous programs.

The `development.runtime` settings are development only: a validator whose
genesis hash names a live cluster refuses to start with them set. Each
is a hard bound, so a validator exits if the cluster turns out to have
more stake or vote accounts than the value allows. Leave headroom.

This profile keeps the existing 64 live slots, account-cache reservation,
and protocol block limits. With bundles disabled the account cache needs
about 2.10 GiB, so its integer-GiB setting must be at least 3. The
transaction cache and live-block pools still cover full-size legal
blocks. The block-size settings under `development.bench` only scale up.

## 4. Assign CPUs and prepare the host

Do not leave `layout.affinity = "auto"` in every config. Each process
would independently choose the same CPUs. Assign disjoint logical CPUs
to the validators, and keep both SMT siblings with the same validator
when possible.

For reference, a successful 96-logical-CPU test used this
machine-specific split, leaving CPUs 0 and 48 for the host:

```text
node 0: 1-15,49-63  (includes spare CPUs for snapshot-production tiles)
node 1: 16-28,64-76
node 2: 29-41,77-89
```

Inspect every topology before reserving memory:

```sh
for cfg in /cluster/node-{0,1,2}.toml; do
  build/native/gcc/*/bin/firedancer-dev --config "$cfg" --alpenglow mem --sort
done
```

The test never configures the host, so standard Firedancer host setup is
a hard prerequisite. Initialize any missing global stages once using
node 0's config. Do not replace the shared keys or genesis with the
configure command's generated development versions.

Then initialize the cluster-specific huge-page mount, CPU partition,
and snapshot directory for each node:

```sh
for cfg in /cluster/node-{0,1,2}.toml; do
  sudo build/native/gcc/*/bin/firedancer-dev --config "$cfg" --alpenglow \
    configure init hugetlbfs cpuset snapshots
done
```

The distinct `hugetlbfs.mount_path` values are intentional: they let each
configure invocation reserve its validator's pages. Total huge pages
must cover the sum of all validators. A shared mount is possible, but
configuring one `min_size` mount only reserves one topology's
requirement.

## 5. Run the cluster

The helper script builds the binaries, configures the host's kernel
limits and each node's huge-page mount, CPU partition, and snapshot
directory, then runs the test. Its Python 3 helper sums all three
topologies' page requirements per NUMA node before allocating the pools.
This matters even with
disjoint CPU affinities: validators can share a NUMA node for buffers
and floating-tile stacks. Invoke it as your normal user; it requests
`sudo` when needed:

```sh
C=/cluster contrib/test/run_fd_cluster.sh

# Longer test on the already configured host:
C=/cluster contrib/test/run_fd_cluster.sh run --root-slot 256 --timeout 300

# Inspect memory, follow logs, or remove the cluster's host resources:
C=/cluster contrib/test/run_fd_cluster.sh mem
C=/cluster contrib/test/run_fd_cluster.sh logs
C=/cluster contrib/test/run_fd_cluster.sh fini
```

It uses the existing `node-0.toml`, `node-1.toml`, and `node-2.toml`,
keys, and genesis. Without `C`, it looks for a `cluster` directory beside
the repository. `--jobs` controls build parallelism. Host resources stay
configured after the test for reuse; `fini` removes the CPU partitions
and huge-page mounts. The `logs` command follows the example profile's
`node-0/firedancer.log` through `node-2/firedancer.log`; use your configured
paths directly if you changed `log.path`.

The snapshot directory is required even when bootstrapping from genesis
with snapshot production disabled. If an earlier setup failed at
`open(.../snapshots)` with `ENOENT`, rerun the helper's `init` command
before `run`; no rebuild or teardown is needed. The `snapshots` configure
stage uses each config's path and creates the directory with the
validator user's ownership and mode `0700`. It preserves existing data.

If an older binary failed to mount node 1 with `ENOMEM` despite ample
RAM, rebuild and run `fini` before retrying. Earlier reservation logic
counted already-reserved pages as available to the next mount, and
counted every stack on every NUMA node. The corrected configure stage
also checks global `free_hugepages - resv_hugepages` before mounting;
NUMA-local free counters alone do not exclude other mounts' promises.

If an older binary reports a waker self-test failure together with an
unconfirmed `/proc/<pid>/syscall` observation, rebuild before diagnosing
the kernel. The cluster's PID namespace retains the host's procfs, so a
namespace-local PID can identify the wrong process there. The self-test
now opens the launcher's own procfs syscall file before forking and
bounds observation to 100 ms, below its 2-second event timeout. The
nested-epoll wakeup and rearm checks remain enabled. These tests need no
huge-page allocation:

```sh
make -j8 test_waker test_waker_self_test
build/native/gcc/*/unit-test/test_waker
build/native/gcc/*/unit-test/test_waker_self_test
```

To invoke the test binary directly after configuring the host:

```sh
sudo env FD_CLUSTER_CONFIGS=/cluster/node-0.toml:/cluster/node-1.toml:/cluster/node-2.toml \
  FD_CLUSTER_ROOT_SLOT=8 \
  build/native/gcc/*/integration-test/test_firedancer_cluster
```

`sudo env` matters: plain `sudo` drops the variables.

The test launches one process per validator, waits for every tile of
every validator to report ready, and then waits for each validator's
replay root slot to reach `FD_CLUSTER_ROOT_SLOT`. The root slot only
advances on finalization, so reaching it means that validator saw enough
of the others to finalize that far.

The test fails if any validator exits, if a validator's tiles do not
come up, or if the root slot is not reached within
`FD_CLUSTER_TIMEOUT_S`. Each validator writes to the `log.path` in its
own config.

All validators run in a PID namespace owned by the test, so they are
torn down with it even if it is killed abruptly.

After the run, optional per-node host cleanup is:

```sh
for cfg in /cluster/node-{0,1,2}.toml; do
  sudo build/native/gcc/*/bin/firedancer-dev --config "$cfg" --alpenglow \
    configure fini cpuset hugetlbfs
done
```
